# 智能体协作

## 1 范围

本规格规定智能体协作的结构与规则，回答满足什么才算成立。

智能体协作是围绕仓库分工的两方结构：owner 执行并持有仓库，reviewer 评审并维护规则。本规格适用于由这两方组成的协作，意图是让协作可被管理、可被追溯、可被替换而不失真。形式化建模到此为止：工具与入口怎么选、派单写成什么格式，属于实现，不在本规格内。

## 2 规则用语

本规格中的「必须」表示强制要求，「不得」表示绝对禁止，「可以」表示明确允许，「应当」表示建议；未满足建议不构成与本规格不一致。

## 3 术语与定义

- owner：执行方，对执行负责，持有仓库。
- reviewer：评审方，对放行负责，维护规则。
- 转发方：可选的居中传话角色，不承担执行责任，不参与放行。
- 仓库：协作的工作区，产物在此封存。
- 产物：交付物，可命名、可封存，附验收标准。
- 对话：两方之间的即时消息通道，不留痕、不作凭证。
- 派单：任务的开立记录，载明对象、任务、交付、合格线与验收人。
- 回传：执行方交回的报告，载明分支、提交与产物路径，与产物同为凭证。
- 验收：放行。reviewer 对照合格线对产物做出的判断，责任由此签署。
- 一轮：从一次派单到其回流收尾的完整过程。

## 4 结构

### 4.1 归属

仓库归 owner 持有，放行权归 reviewer。两方不得合并：治理只认责任，owner 对执行负责，reviewer 对放行负责；合并即自评自签，评审失效。

### 4.2 凭证与账本

产物与回传是协作的凭证，一律封存进仓库；对话不是凭证。仓库兼作账本：每轮协作留下可查的记录——分支、提交、产物路径。谁开的、走过哪站、谁放的行，事后都能查到。

### 4.3 连接方式

消息面承载派单与回传，可以两方直连，也可以设一个转发方居中：

```text
产物面：owner ──产物──> 仓库 ──产物──> reviewer
消息面：reviewer ──派单/回传──> owner             （直连：无转发方）
消息面：reviewer ──派单/回传──> 转发方 ──> owner  （转发：回传沿原路）
```

判断的依据只有两种：仓库里的产物原件，或回传里的转述。依据前者为直连，依据后者为转发；结构的分界在判断依据，不在设备，也不在是否用工具传话。两种连接方式共用同一个产物面，凭证一律进仓。

## 5 环节

一轮协作依次经过五站，规则的编号标注在各站之后：

```text
派单(R6) → 执行 → 交付入仓(R2) → 验收(R5) → 回流(R7)
```

交付入仓由 owner 完成，验收由 reviewer 做出；执行可以委派，放行不可委派。转发方只出现在消息面上，不出现在任何一站的责任里。R1、R3、R4 是恒定约束，全程成立，不专属一站。

## 6 规则

- R1 责任分离：owner 与 reviewer 必须由不同主体承担，不得合并。
- R2 凭证落仓：每轮交付必须以产物形式进入仓库，可按分支、提交与产物路径追溯；留在对话里的结果不是凭证，不算交付。
- R3 对话限令：对话只传指令与问询，不得承载交付。
- R4 转发方限令：转发方只转传派单与回传，不得代做判断，不得改写传话内容。
- R5 放行归属：执行可以委派，放行不得委派；验收必须由 reviewer 直接做出。
- R6 派单自足：派单必须载明对象、任务、交付、合格线与验收人，附上仓库、分支等执行上下文，使 owner 不读对话也能执行；转发结构下还必须载明失败回传方式。
- R7 回流归档：评审结论必须转成下一轮派单，或写入规则与档案；账本由此连续，事后可查。

## 7 一致性

满足以下全部条件的协作，符合本规格：

1. 两方可指认，互不兼任（R1）。
2. 每轮交付都能在仓库里按分支、提交与产物路径追溯（R2）。
3. 每条验收结论都能追溯到仓库里的产物，而不是某段对话（R2、R3、R5）。
4. 撤除转发方后协作仍然成立：传话改由人手工承担，责任归属不变（R4、R5）。
5. 任何一轮都以回流收尾：转成下一轮派单，或写入规则与档案（R7）。

## 附录 A 连接方式的取舍

本附录为资料性内容，不影响一致性判定。

直连结构最扁平：判断直接落在仓库产物上，代价是人工操作多，从查收到回流全靠手工衔接。转发结构省人工：派单与回传由转发方携带，但判断建立在转述上，多一层转发多一道失真，失败定位也要人工排查，结构上不如直连理想。取舍恒定：转发每省一分人工，判断就多经一道转述。
