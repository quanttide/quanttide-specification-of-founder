# 智能体协作

智能体协作是人与智能体围绕仓库分工的两方结构：owner 执行并持有仓库，reviewer 评审并维护规则。本规格定义这种协作的角色、结构与规则，回答满足什么才算成立。派单怎么写、入口怎么选属于做法，具体案例收在案例集。

## 术语

- owner：执行方。领取派单，执行任务，把产物提交进仓库。
- reviewer：评审方。发出派单，对照产物做判断，维护规则。
- 转发方：可选的居中角色。替两方转传派单与回传。
- 仓库：两方之间唯一的交接点，产物的存放处。
- 产物：交付评审的工作结果，如代码、文档、数据。
- 对话：两方之间的即时消息通道。
- 派单：reviewer 发出的任务说明。
- 回传：owner 执行后沿消息面返回的报告。
- 验收：reviewer 对照合格线对产物做出的判断。

## 结构

协作分两个面。产物面是交接：owner 把产物提交进仓库，reviewer 从仓库查收。消息面是传话：派单与回传沿它往来，可以两方直连，也可以设一个转发方居中。

```text
产物面：owner ──产物──> 仓库 ──产物──> reviewer
消息面：reviewer ──派单──> owner             （直连：无转发方）
消息面：reviewer ──派单──> 转发方 ──> owner  （转发：回传沿原路）
```

判断的依据只有两种：仓库里的产物原件，或回传里的转述。依据前者为直连，依据后者为转发。结构的分界在这里，不在设备，也不在是否用工具传话。

直连结构最扁平，也是理想模式：reviewer 直接对照仓库产物做判断。移动端工作流属于这种——电脑端执行推送，手机端拉取仓库查收评审；派单即使经 Hermes 传话，判断也不经转述。代价是人工操作多，从查收到结论回流全靠手工衔接。

转发结构省人工：reviewer 凭回传验收，判断沿消息面经转述落地。后台派单属于这种——Hermes 转发，Pi 执行，人验收。派单与回传由转发方携带，人工最省；判断却建立在转述上，多一层转发多一道失真，失败定位也要人工排查。结构上不如直连理想。

两种连接方式共用同一个产物面：产物一律先进仓库，无论消息面怎么连。

## 规则

规则分两类：恒定约束全程成立，轮次约束在一轮内按序出现。

```text
一轮：派单(R6) → 执行 → 交付入仓(R2) → 查收 → 验收(R5) → 回流(R7)
恒定：角色分离(R1) · 对话不存结果(R3) · 转发方不判断(R4)
```

- R1 角色分离：owner 与 reviewer 不得由同一体承担。两方合并即自评，评审失效。
- R2 交付落仓：每轮交付必须以产物形式进入仓库，可按分支、提交与产物路径定位；留在对话里的结果不算交付。
- R3 对话限令：对话只传指令与问询，不承载交付。
- R4 转发方限令：转发方只转传派单与回传，不得代做判断，不得改写转传内容。
- R5 判断归属：执行可以委派，判断与验收不可委派；验收必须由 reviewer 直接做出。
- R6 派单自足：派单必须写明对象、任务、交付、合格线与验收人，附上仓库、分支等执行上下文，使 owner 不读对话也能执行；转发结构下还须写明失败回传方式。
- R7 结论回流：评审结论必须转成下一轮派单，或写入规则与档案；停在评审这一步，该轮协作不产生留存收益。

## 怎么算成立

1. 两方可指认，互不兼任（R1）。
2. 每轮交付都能在仓库里按分支、提交与产物路径定位到（R2）。
3. 每条验收结论都能追溯到仓库里的产物，而不是某段对话（R2、R3、R5）。
4. 转发方可以随时撤除：撤除后派单与回传改由人手工搬运，判断不受影响（R4、R5）。
5. 任何一轮都以回流收尾：转成下一轮派单，或写入规则与档案（R7）。

## 不做什么

- 不定义工具与入口：Hermes、Pi、Working Copy 的选择与分工见案例集。
- 不定义派单与回传的逐字模板：案例集收有模板。
- 不定义结论回流的自动化：回流目前靠人工衔接。
- 不定义多方扩展：本规格只覆盖两方结构，多 owner 与多 reviewer 另立一篇。
